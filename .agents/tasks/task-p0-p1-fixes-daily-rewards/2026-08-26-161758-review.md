# P0/P1 bug fixes and Daily Rewards system for Battle Pets

This branch fixes two P0 exploit vectors (crit QTE replay and untargeted pet damage), two P1 quality issues (duplicate zone geometry and stacking egg-prompt handlers), and adds a 7-day Daily Rewards feature with server-authoritative UTC validation. The approach is conservative: each fix touches the minimum surface area needed, the Daily Rewards service follows the existing singleton pattern, and the build tool diff is almost entirely deletions. Watch for: the Boost reward on Day 3 grants a flat 250 coins instead of activating a real timed buff (confirmed); the crit token is keyed per-destructible so a player holding tokens for two different destructibles can use both (likely fine, but differs from "exactly one crit per click" if click targets differ); and `critToken` is accepted as `nil` by the Main.server.lua handler, meaning old clients without token support would reach `critAttackDestructible` and be rejected there rather than at the parameter gate (confirmed, low risk since the function rejects nil tokens early).

**Verdict**: APPROVED

## High-level view

The crit exploit is closed with a GUID-based one-shot token: `clickAttackDestructible` generates it, returns it to the client, and `critAttackDestructible` consumes it exactly once. The token is backed by a time-window check as secondary validation, so even a replayed token fails after 2 seconds. A usability quirk exists: rapid clicking overwrites the server-side token while the client's crit button still holds the old one, causing silent crit failures — not exploitable, but potentially confusing.

Pet targeting validation was already implemented prior to this branch; the new addition is a 0.1-second rate limit on `AssignPetTarget` in Main.server.lua, preventing client-side spam from flooding the server with assignment updates.

Static zone geometry (Zone1–Zone8 baseplates and ZoneGate2–ZoneGate8 pillars/barriers) is removed from `generate_rbxlx.py`. ZoneService already creates all this at runtime, so the deletion eliminates doubled ground planes and colliders.

Egg prompt connections are tracked in a module-level `_eggPromptConnections` array that is disconnected and cleared at the start of every `connectEggPrompts()` call, preventing accumulation across respawns.

Daily Rewards uses a 7-day cycle with UTC day-boundary math (`os.time() / 86400`), streak reset after 2+ missed days, and a 5-second rate limit on the claim remote. A player who claims at 23:59 UTC can claim again at 00:01 UTC (2 minutes later) — intentional by design but surprising in non-UTC timezones.

## Crit token stale-button race

The client's `fireClickDamage` guards crit button spawning with `effectsController:hasCritButtonActive()`. Rapid clicking while a crit button is visible does NOT spawn a new button, but the server-side token IS overwritten on each click. The token embedded in the visible crit button becomes stale on the server. The crit will fail silently — no visual feedback, the player just misses the crit opportunity. This matches the stated security goal (one crit per click, one-shot) but creates a usability gap where fast clickers never land crits.

```
Client click → InvokeServer(destructibleId)
              ← (true, critToken)

Client presses crit button → InvokeServer(destructibleId, critToken)
              ← (true/false)
```

## Day 3 Boost reward is a placeholder

`DailyRewardService.awardReward` handles `type == "Boost"` by granting 250 coins:

```lua
elseif rewardDef.type == "Boost" then
    if DailyRewardService._currencyService then
        DailyRewardService._currencyService.addCoins(player, 250)
    end
```

The description shown to the player is "2x Coins Boost (30 min)" but they receive 250 coins. If this ships to players, Day 3 will feel broken. ShopService already has a timed buff mechanism for speed potions that could be reused here.

## Egg prompt vs campaign portal asymmetry

The campaign portal `Touched` handler (inside `onCharacterAdded`) reconnects on every respawn without disconnecting old handlers. This is pre-existing behavior and out of scope, but the new dedup pattern on egg prompts highlights the inconsistency — the campaign handler accumulates connections that will fire redundantly on subsequent respawns.
