# Battle Pets: Full game replacement from SHIFT//BREAK to Pet Simulator + Campaign

The entire SHIFT//BREAK codebase is gutted and replaced with "Battle Pets," a pet-simulator game with 8 themed zones, egg hatching, pet inventory management, and a lane-based campaign side-mode (Battle Cats style). The architecture is server-authoritative: every mutation flows through RemoteFunctions validated on the server, currency is never modified client-side, and the campaign tick runs on Heartbeat server-side. A Python generator produces a standalone `.rbxlx` file embedding all Luau source plus procedural world geometry.

Watch for: **Missing `BindToClose` handler means player data is lost on server shutdown (confirmed)**. Race condition between EggService balance check and PetService coin deduction can allow hatching with insufficient funds (likely). Campaign battle tick applies DPS every frame without a cooldown, making combat frame-rate-dependent (confirmed). DestructibleDamaged/Destroyed events fire only to the attacking player, so other players in the same zone never see damage (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The data layer caches everything in a flat `_cache[UserId]` table with no session-locking or fail-safe flag—unlike the old DataService which tracked whether a load succeeded and refused to save corrupted state. Most critically, `game:BindToClose` is missing, so a server-initiated shutdown (deploy, crash, Roblox maintenance) will silently drop all unsaved progress for every online player.

The service dependency graph has a circular initialization: CurrencyService is initialized with `nil` for its upgradeService reference, which is patched afterward via `CurrencyService._upgradeService = UpgradeService`. This works at runtime because upgrade lookups only happen during gameplay (not init), but it's a fragile coupling—any future init-time calculation that touches upgrade bonuses will silently produce zero.

The campaign combat system runs a full simulation per player on Heartbeat. Damage is applied as `damage * dt` every frame with no attack-cooldown or tick-rate normalization. Entities at 240 fps deal roughly four times the DPS of entities at 60 fps. Victory/defeat rewards are awarded unconditionally without verifying whether they were already granted in a previous frame (the flag `battle.active = false` prevents re-entry, but only after the current tick completes).

The zone destructible system is server-owned and respawns objects on a 10-second timer, but damage and destruction events are unicast to the attacking player. In a multiplayer session, other players in the same zone see an intact object that is actually dead on the server.

The egg-hatching flow in EggService checks balance, fires a client animation event, `task.wait(2)`, then delegates to PetService which performs the actual deduction. During those 2 seconds, a player could spend their coins elsewhere, and PetService's `removeCoins` would fail—leaving the player with a hatching animation but no pet, or (if the balance check in EggService is relied upon as the gate) allowing a negative-balance exploit if another purchase sneaks in.

The client-side destructible click handler raycasts for objects in a `workspace.Destructibles` folder that is never created by the server—ZoneService places objects in `workspace.Zones.Zone_N`. The click-to-attack path is dead code as written.

1. **No `BindToClose` in DataService** — Player data is lost on server shutdown. Add `game:BindToClose(function() ... save all ... end)` in Main.server.lua or DataService.
2. **Campaign DPS is frame-rate-dependent** — `pet.damage * dt` with no attack interval makes combat outcomes vary with client/server FPS. Introduce an attack cooldown (e.g., 1-second interval) and deal fixed damage per attack.

7. **Config missing Epic deploy cost** — `Config.Campaign.PetDeployCosts` has Common/Uncommon/Rare/Legendary but no Epic, while the rarity system includes Epic pets. Deploying an Epic pet in campaign will hit a nil cost.

## DataService: persistence gaps

The new DataService drops two safety mechanisms the old version had:

1. **`BindToClose`**: The old DataService bound to `game:BindToClose` to flush all player saves before the server exits. The new version has only `PlayerRemoving` (which doesn't fire on server shutdown) and a 60-second auto-save loop. Any progress since the last auto-save is lost on shutdown. This is a data-loss bug in production.

2. **Load-failure protection**: The old DataService tracked `_canSave[player]` and refused to persist data if the initial load failed (protecting against overwriting a real save with defaults). The new version on load failure sets defaults into `_cache` and will happily overwrite real data on the next save cycle.

```lua
-- Missing from the new DataService:
game:BindToClose(function()
    for _, player in ipairs(Players:GetPlayers()) do
        DataService.savePlayerData(player)
    end
end)
```

There's also no retry logic on `GetAsync`—the old version tried 3 times with backoff.

## Campaign combat: frame-rate-dependent DPS

In `CampaignService._updateBattle`, both pet and enemy damage is computed as:

```lua
closestEnemy.hp = closestEnemy.hp - pet.damage * dt
```

On a server running at 60 Hz this produces consistent results, but Roblox Heartbeat frequency can vary under load (and drops to ~30 Hz on mobile). More importantly, pets that reach the enemy base deal `pet.damage * dt` every frame indefinitely—they're never consumed or stopped. A single pet parked at `position >= LANE_LENGTH` will drain the enemy base at continuous DPS forever.

A standard fix: track an `attackCooldown` per entity, decrement by `dt`, and only deal damage (as a fixed value) when the cooldown expires.

## Destructible visibility in multiplayer

ZoneService fires `DestructibleDamaged` and `DestructibleDestroyed` events only to the attacking player:

```lua
event:FireClient(player, destructibleId, destructible.hp, destructible.maxHp)
```

Other players in the zone continue to see and interact with a destructible that no longer exists server-side. When they attempt to attack it, the server returns "Destructible not found." The fix is either `FireAllClients` or replicating HP via Part attributes that all clients can observe.

## Egg hatching TOCTOU

The EggService orchestration:

```
1. Check balance >= cost          (EggService.purchaseAndHatch)
2. Fire EggHatchStart to client   (cosmetic)
3. task.wait(2)                   (server-side yield)
4. Call PetService.hatchEgg       (actually deducts coins)
```

Between steps 1 and 4, another RemoteFunction call (upgrade purchase, zone unlock, another egg) can spend the same coins. If PetService.removeCoins then fails, `hatchEgg` returns an error—but the client already received `EggHatchStart` and is mid-animation. The player sees a hatch animation that produces nothing.

The server yield in a RemoteFunction handler is also problematic because it blocks the invoking client's response for 2 seconds. Moving the deduction to before the `task.wait`, or using a per-player mutex, would fix both issues.

## Client raycast targeting dead path

In `Main.client.lua`:

```lua
local destructiblesFolder = workspace:FindFirstChild("Destructibles")
if destructiblesFolder and hit:IsDescendantOf(destructiblesFolder) then
```

But ZoneService creates `workspace.Zones.Zone_1`, `workspace.Zones.Zone_2`, etc. No `Destructibles` folder ever exists. The click handler will never match, making manual click-to-attack inoperable. The auto-attack path via `PetController:getNearestDestructible` likely has the same problem (searches a folder that doesn't exist).

## Missing Epic rarity in campaign deploy costs

`Config.Campaign.PetDeployCosts` defines costs for Common, Uncommon, Rare, and Legendary. The rarity system in `Config.RarityWeights` includes Epic (4% weight). When `CampaignService.deployPet` looks up the deploy cost:

```lua
local deployCost = CampaignData.DeployCosts[petInstance.rarity]
```

For an Epic pet, `deployCost` is `nil`, and the subsequent `battle.energy < deployCost` comparison raises an error, crashing the deploy for that player.

## Service initialization coupling

The circular dependency between CurrencyService and UpgradeService is resolved by a two-phase init plus a direct field assignment:

```lua
CurrencyService.init(DataService, nil)
UpgradeService.init(DataService, CurrencyService)
CurrencyService._upgradeService = UpgradeService
```

This works because `applyBonuses` in CurrencyService checks `if CurrencyService._upgradeService then` before using it. If a future developer adds upgrade-dependent logic to `CurrencyService.init`, it will silently get zero bonuses. The pattern would be clearer as an explicit `lateInit` or `setUpgradeService` method.
