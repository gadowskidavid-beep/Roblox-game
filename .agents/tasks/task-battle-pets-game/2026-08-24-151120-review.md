# Battle Pets: v2 review — fix verification and remaining client-server contract issues

All 7 issues from the v1 review have been addressed: DataService now has `BindToClose` with a `_canSave` guard and retry logic, campaign combat uses a fixed-interval `ATTACK_COOLDOWN` instead of per-frame DPS, destructible events use `FireAllClients`, egg hatching deducts coins before the animation delay with a per-player lock, the click handler raycasts into `workspace.Zones`, and `CampaignData.DeployCosts` includes Epic. The fixes are structurally correct on the server side.

Watch for: **Client-server data contract mismatches make the attack path and pet visuals non-functional (confirmed)**. `sendPetToAttack` passes a Part instance to `InvokeServer` but the server expects a string ID, so every click-to-attack call is rejected. The `PetEquipped`/`PetUnequipped` events send a single object/string but the client handler expects an array with `.uniqueId` fields, breaking pet orbit visuals. `PetController:getNearestDestructible` still searches `workspace.Destructibles` (a folder that doesn't exist), so proximity auto-attack is dead code. Each equipped pet fires a separate `AttackDestructible` call, but the server calculates ALL equipped pets' damage per call—creating an N× damage amplification exploit **(likely)**.

**Verdict**: NEEDS_CHANGES

## High-level view

The v1 server-side fixes are all sound: persistence is safe, campaign DPS is frame-rate-independent, egg hatching is race-free, and destructible events broadcast to all players. The server logic is in good shape.

The remaining problems are concentrated in the client-server contract layer. The server switched from unicast to broadcast and from Instance references to string IDs for destructibles, but the client handlers still expect Part instances. The pet equip/unequip event payloads don't match what `PetController:updateEquippedPets` iterates over. And `PetController:getNearestDestructible` still targets a nonexistent `workspace.Destructibles` folder (the v1 fix corrected the click handler in `Main.client.lua` but missed this helper method). These mismatches collectively mean that while the server is correct and secure, the client-side visuals for pets and the primary attack interaction path are non-functional.

A secondary concern: each equipped pet fires its own `AttackDestructible` remote call on click, but the server's `ZoneService.attackDestructible` sums damage from ALL equipped pets per invocation. With 6 pets equipped, one click fires 6 calls dealing 6× the intended squad damage. The fix is straightforward—fire one call per click, not one per pet.

## Attack path type mismatch

The click handler in `Main.client.lua` correctly identifies the hit Part inside `workspace.Zones`, verifies it has a `DestructibleId` StringValue child, then calls:

```lua
for uniqueId, _ in pairs(petController._equippedPets) do
    petController:sendPetToAttack(uniqueId, hit)
end
```

`sendPetToAttack` receives `hit` (a Part) and eventually calls:

```lua
attackRemote:InvokeServer(destructible)
```

On the server, the handler is:

```lua
getRemoteFunction("AttackDestructible").OnServerInvoke = function(player, destructibleId)
    if type(destructibleId) ~= "string" then
        return false, "Invalid destructible ID parameter"
    end
    ...
end
```

Roblox serializes Instance references across the remote boundary (sending a Part is valid in Roblox networking), but its type on the server is `Instance`, not `"string"`. The guard rejects every attack. The click handler already has the string value available (`hit:FindFirstChild("DestructibleId").Value`); it should pass that string to `sendPetToAttack` instead of the Part.

## Damage amplification via per-pet remote calls

Even if the type mismatch is fixed, the loop fires one `AttackDestructible` per equipped pet. On the server, `ZoneService.attackDestructible` calculates total damage from ALL equipped pets:

```lua
for _, pet in ipairs(equippedPets) do
    totalDamage = totalDamage + ZoneService._petService.getPetDamage(pet, player)
end
destructible.hp = destructible.hp - totalDamage
```

With 6 pets equipped, one click produces 6 invocations × full squad damage = 6× intended DPS. This is exploitable: a malicious client could fire the remote in a loop. The fix is either (a) fire one remote call per click, or (b) add a server-side per-player attack cooldown that rate-limits calls regardless of client behavior.

## Pet equip/unequip event shape mismatch

Server `PetService.equipPet` fires:

```lua
event:FireClient(player, pet)  -- pet = {id = "...", petId = "...", name = "...", ...}
```

Server `PetService.unequipPet` fires:

```lua
event:FireClient(player, petInstanceId)  -- a bare string
```

The client handler in Main.client.lua passes these directly to `petController:updateEquippedPets(equippedPets)`, which does:

```lua
for _, petData in ipairs(equippedList) do
    newIds[petData.uniqueId] = true  -- petData.uniqueId is always nil; the server uses .id
end
```

On `PetEquipped`, `equippedList` is a single table (not an array), so `ipairs` yields nothing. On `PetUnequipped`, it's a string, so `ipairs` also yields nothing. Pet models are never created or removed after the initial load, and the initial load also fails because `playerData.equippedPets` is an array of string IDs, not pet-data objects.

## getNearestDestructible still dead

The v1 review flagged that `Main.client.lua` targeted `workspace.Destructibles`. That was fixed in the click handler (now checks `workspace.Zones`). But `PetController:getNearestDestructible` (used in the RenderStepped loop for proximity auto-attack and progress bar display) still searches `workspace.Destructibles`:

```lua
local destructiblesFolder = workspace:FindFirstChild("Destructibles")
if not destructiblesFolder then return nil end
```

This means the auto-proximity progress bar display is dead code. The click-to-attack path works (modulo the type issue above), but the passive "show HP bar when near a destructible" never triggers.

## Destructible event parameter mismatch

The server now correctly calls `FireAllClients` (addressing the v1 unicast issue), but passes the destructible's string ID as the first argument:

```lua
event:FireAllClients(destructibleId, destructible.hp, destructible.maxHp)
event:FireAllClients(destructibleId, destructible.drops)
```

The client handlers receive this string and attempt:

```lua
if destructible and destructible:IsA("BasePart") then
```

A string is truthy but doesn't have `:IsA`, so this errors silently (pcall-wrapped by Roblox event dispatch). Progress bars and currency popups never appear for any player. The client needs to resolve the string ID back to a Part (e.g., by searching workspace for a Part named `"Destructible_" .. destructibleId`) or the server should send the Part reference directly.
