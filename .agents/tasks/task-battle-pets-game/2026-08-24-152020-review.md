# Battle Pets: v3 review — event payload mismatches remain

The v2 review's 5 issues (attack remote type, per-pet damage amplification, PetEquipped/Unequipped handling, getNearestDestructible folder, and string-vs-Part in destructible events) were all resolved in commit 8120183. The server-side architecture is sound and the v1/v2 fixes are intact.

Watch for: **Four client-server event payload mismatches break the currency display, upgrade UI, campaign victory screen, and egg hatch animations (confirmed)**. The server fires `CurrencyUpdated` with a single table argument, but the client destructures into two positional arguments. Similar shape mismatches exist for `UpgradeUpdated`, `CampaignVictory`, and the egg hatch events. These are purely client-side display bugs—no data loss or security issues—but they make core feedback loops non-functional.

**Verdict**: NEEDS_CHANGES

## High-level view

The remaining issues are all in the event-handler layer where the server's `FireClient` call signature doesn't match what the client's `OnClientEvent:Connect` callback expects. CurrencyService passes a single `{coins, diamonds}` table but the client unpacks into two positional args. UpgradeService passes `(upgradeId, level)` but the client expects a single table. CampaignService passes `(levelNum, rewards)` but the client expects just `(rewards)`. The egg hatch flow has a position parameter that was never wired. These mismatches prevent the UI from updating after currency changes, upgrades, victories, and hatch results—all core gameplay feedback loops.

<details>
<summary>Issues (4)</summary>

1. **CurrencyUpdated sends table, client expects two args** — CurrencyService fires `FireClient(player, { coins = ..., diamonds = ... })`. The client handler destructures as `function(coins, diamonds)`, so `coins` receives the full table (displays as a stringified table address) and `diamonds` is nil. Fix: either send two args from the server (`event:FireClient(player, data.coins, data.diamonds)`) or unwrap the table on the client.
2. **UpgradeUpdated sends (upgradeId, level), client expects (upgrades table)** — UpgradeService fires `event:FireClient(player, upgradeId, data.upgrades[upgradeId])`. The client handler is `function(upgrades)` which receives the string `upgradeId`, then passes it to `UIController:updateUpgrades` which iterates it as a table. Fix: send the full `data.upgrades` table from the server, or change the client handler to accept `(upgradeId, level)` and update incrementally.
3. **CampaignVictory sends (levelNum, rewards), client expects (rewards)** — CampaignService fires `event:FireClient(player, battle.levelNum, battle.levelDef.rewards)`. The client handler is `function(rewards)` which receives `levelNum` (a number) and passes it to `campaignController:onVictory`. The rewards table is silently dropped. Fix: swap argument order or adjust the client to accept both args.
4. **EggHatchStart/EggHatchResult position parameter missing** — EggHatchStart fires `(eggType)` but the client expects `(eggPosition, eggType)`. EggHatchResult fires `(newPet)` but the client expects `(petData, eggPosition)`. The animation code guards with `if eggPosition then` so it degrades to no animation, but the hatch flow is visually incomplete. Fix: include a position vector in both server events, or remove the position parameter from the client handler and use a fixed screen-space animation.

## CurrencyUpdated payload shape

Every call to `CurrencyService.addCoins`, `removeCoins`, `addDiamonds`, or `removeDiamonds` fires the same event:

```lua
event:FireClient(player, { coins = data.coins, diamonds = data.diamonds })
```

The client handler in `Main.client.lua`:

```lua
CurrencyUpdated.OnClientEvent:Connect(function(coins, diamonds)
    uiController:updateCurrency(coins, diamonds)
end)
```

In Roblox's remote event serialization, the single table argument maps to the first parameter `coins`. The second parameter `diamonds` receives nil. `UIController:updateCurrency` then calls `tostring(coins or 0)` on a table, producing something like `"table: 0x..."` in the label. This affects every coin/diamond transaction in the game—attacking destructibles, hatching eggs, zone unlocks, campaign rewards.

The simplest fix is changing the server to send two positional arguments: `event:FireClient(player, data.coins, data.diamonds)`.

## UpgradeUpdated incremental vs. full-state

The server sends a delta update (one upgrade changed):

```lua
event:FireClient(player, upgradeId, data.upgrades[upgradeId])
```

The client treats the first argument as the full upgrades table and replaces `self._upgradeData`:

```lua
UpgradeUpdated.OnClientEvent:Connect(function(upgrades)
    uiController:updateUpgrades(upgrades)
end)
```

```lua
function UIController:updateUpgrades(upgrades)
    self._upgradeData = upgrades or {}
    self:_refreshUpgradeGrid()
end
```

After any upgrade purchase, `self._upgradeData` becomes a string (the upgradeId), and `_refreshUpgradeGrid` iterates over characters of that string instead of upgrade entries. The fix is either sending `data.upgrades` (full table) from the server so the client's full-replace strategy works, or changing the client to `function(upgradeId, level)` and doing `self._upgradeData[upgradeId] = level`.

## CampaignVictory argument order

Server (`CampaignService._onVictory`):

```lua
event:FireClient(player, battle.levelNum, battle.levelDef.rewards)
```

Client:

```lua
CampaignVictory.OnClientEvent:Connect(function(rewards)
    campaignController:onVictory(rewards)
end)
```

`rewards` receives the number `battle.levelNum`. `CampaignController:onVictory` tries to read `.Coins` and `.Diamonds` fields from a number, silently producing nil values. The victory screen won't display reward amounts.

## Egg hatch flow missing position context

The server fires `EggHatchStart` with just the egg type string, and `EggHatchResult` with just the pet data table. The client handlers expect a position vector as either the first or second argument. Since neither event provides a position, the guard `if eggPosition then` prevents the animation from playing. The hatch still "works" (pet is added to inventory) but the visual feedback is absent. The server could compute the egg's world position from ZoneService's egg placement data and include it in both events.
