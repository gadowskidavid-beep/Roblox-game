# Pet damage activation and crit token consumption fix

Two P0 bug fixes addressing broken pet damage and an exploitable crit system. Pet damage was non-functional because the client never called the `AssignPetTarget` RemoteFunction that the server's `attackDestructible` already gated on — pets were visually attacking but dealing zero damage. The crit token was reusable because the server kept the crit window open after consumption, allowing multiple crit hits from a single circle click. The fix wires up `AssignPetTarget` calls throughout PetController's lifecycle and consumes the crit window immediately upon use.

Watch for: race condition between assignment and attack on first manual click (possible, mitigated by Roblox FIFO); unacknowledged `InvokeServer` failures silently leave stale `_serverAssignments` entries (confirmed); no server-side cleanup of `_petTargets` when a destructible is destroyed (confirmed).

**Verdict**: APPROVED

## High-level view

The pet damage fix is structural: `ZoneService.attackDestructible` already required pets to be registered in `_petTargets[userId]` before counting them toward damage, but nothing on the client ever populated that table. Adding `InvokeServer` calls at every point where `_attackingPets` transitions (assign or clear) closes that gap. The deduplication via `_serverAssignments` avoids flooding the server with redundant calls on every heartbeat frame.

The crit fix consumes `playerCritWindows[destructibleId]` immediately after validation, converting the system from "multiple hits within a time window" to "exactly one hit per circle click." The old behavior allowed a scripted client to fire unlimited `CritAttackDestructible` calls within the window — the 0.2s rate limit capped throughput but didn't eliminate the exploit.

The `_serverAssignments` table on the client is maintained optimistically (set before server confirmation) but never reconciled if `InvokeServer` fails or the server rejects the assignment. This doesn't cause incorrect damage (the server is authoritative) but could cause the client to skip future assignment calls because it thinks the server already knows.

<details>
<summary>Issues (3)</summary>

1. **Stale `_serverAssignments` on InvokeServer failure** — If the server rejects an `AssignPetTarget` call (pet not equipped, destructible gone), the client's `_serverAssignments[uniqueId]` still reflects the requested target. Subsequent calls to `sendPetToAttack` with the same target will skip the `InvokeServer` because the deduplication check passes. Wrap the spawn in a pcall and clear the entry on failure or rejection.
2. **Server `_petTargets` not cleaned when destructible is destroyed** — When a destructible reaches 0 HP in `attackDestructible`, the server removes it from `_destructibles` and schedules respawn, but never clears entries in `_petTargets` that reference that destructible ID. If the destructible respawns with the same ID (it does — the respawn reuses `destructibleId`), stale entries may cause pets to "already be assigned" to a target the client has since moved away from, with damage counting toward the wrong (respawned) destructible until the client's next heartbeat clears them.
3. **Repeated inline pattern for clearing assignments** — The 6-line block (nil `_serverAssignments`, `task.spawn` InvokeServer nil) is duplicated ~10 times. Extract to a helper like `self:_clearServerAssignment(petId)`. Not a correctness issue but increases the chance of a future maintenance error where one instance is updated and others aren't.

## Assignment-attack ordering in the manual click path

In `sendOnePetToTarget`, the sequence is: `sendPetToAttack(...)` → `fireAttackRemote(...)`. Inside `sendPetToAttack`, the server call is wrapped in `task.spawn`, which in Roblox executes the spawned function synchronously up to its first yield (`InvokeServer`). This means the `AssignPetTarget` network message is dispatched before `fireAttackRemote` dispatches `AttackDestructible`. Roblox's server processes remote invocations from a single client in FIFO order, so the assignment is registered before the attack is evaluated. Under abnormal network conditions (packet reordering at the transport layer), the first manual click could theoretically miss — but this would require conditions outside normal Roblox networking guarantees.

## Optimistic `_serverAssignments` and silent failures

```lua
if self._assignPetTarget and self._serverAssignments[uniqueId] ~= destructibleId then
    self._serverAssignments[uniqueId] = destructibleId
    task.spawn(function()
        self._assignPetTarget:InvokeServer(uniqueId, destructibleId)
    end)
end
```

The entry is set before the server responds. If `InvokeServer` returns `false` (e.g., "Pet not found or not equipped"), the client still believes the assignment is active. The next call to `sendPetToAttack` with the same destructible will hit the `~= destructibleId` guard and skip the server call entirely. In practice this matters when a pet is unequipped mid-combat — the client's stale entry prevents re-assignment after re-equip.

A minimal fix: check the return value inside the spawn and clear on failure:

```lua
task.spawn(function()
    local ok = self._assignPetTarget:InvokeServer(uniqueId, destructibleId)
    if not ok then
        self._serverAssignments[uniqueId] = nil
    end
end)
```

## Destructible destruction and `_petTargets` lifecycle

When `attackDestructible` destroys a destructible (hp ≤ 0), the server removes it from `ZoneService._destructibles` and schedules a 10-second respawn that reuses the same `destructibleId`, but never clears entries in `_petTargets` that reference that ID. The client handles this correctly (the auto-attack loop detects the missing destructible and clears the target on the next heartbeat), but there's a window between server destruction and client cleanup where stale assignment data persists. If the destructible respawns within that window and a pet attack fires, the server would apply damage to the fresh destructible using an assignment the player didn't intentionally make against the new instance.

## Crit window consumption

The old behavior allowed a scripted client to fire unlimited `CritAttackDestructible` calls within the time window. The 0.2s rate limit (`CRIT_ATTACK_COOLDOWN`) limited exploit throughput to ~5 crits per window but didn't eliminate the exploit. Consuming the window immediately (`playerCritWindows[destructibleId] = nil` at line 1881) makes the rate limit irrelevant for exploit prevention — the window is gone after one use regardless of timing. This is a fail-closed design: even if the crit-circle UI glitches and fires twice, only the first hit applies.
