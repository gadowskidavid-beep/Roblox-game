# Shiny/Rainbow variant system for pet hatching

Adds a rare-variant layer to egg hatching: Rainbow (0.1%) and Shiny (1%) chances, boosted by the existing LuckyEggs upgrade. Variant pets get damage multipliers (Shiny 3×, Rainbow 5×) applied both at creation time and at runtime, discovery keys follow the existing `Golden_` prefix pattern, the Pet Index drops its "Coming Soon" gates, and the hatch reveal animation gains variant-colored flashes. Watch for: **damage multipliers are applied twice** — once baked into `pet.damage` at hatch, then again in `getPetDamage` at runtime — resulting in 9× for Shiny and 25× for Rainbow instead of the intended 3×/5× (confirmed). The same double-application also affects Golden pets via the newly added `pet.golden` check in `getPetDamage` (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The variant rolling in `hatchEgg` multiplies `petDef.baseDamage` by the variant factor and stores the result in `pet.damage`. Then `getPetDamage` reads `pet.damage` and multiplies by the variant factor again. This means Shiny pets deal 9× base damage and Rainbow pets deal 25× base damage in practice. The fix is straightforward: either remove the multiplier from `hatchEgg` (store `petDef.baseDamage` as-is and let `getPetDamage` handle scaling) or remove the variant/golden multipliers from `getPetDamage` and keep the baked value as the source of truth. The same logic bug applies to Golden: `convertToGoldenPet` already stores `baseDamage * 2` in `pet.damage`, and the new `if pet.golden then baseDamage = baseDamage * 2` doubles it again at runtime.

The `luckyMultiplier` calculation treats `getUpgradeBonus` returning 0 as "no bonus" and defaults to 1 — but the semantic contract of that return value matters. If the upgrade service returns a *multiplier* (e.g., 2.0 means "double luck"), the current math is correct. If it returns an *additive bonus* (e.g., 0.5 means "+50%"), the formula should be `chance * (1 + luckyBonus)`. Worth verifying against the upgrade data definitions.

The hatch reveal replaces the rarity label ("Legendary", "Common") with "SHINY" or "RAINBOW" for variant pets, meaning the pet's actual rarity is no longer visible on the reveal screen. Players may want to see both.

## Double-baked damage in hatchEgg and getPetDamage

In `PetService.hatchEgg`, the code sets:

```lua
if variant == "Shiny" then
    petDamage = petDef.baseDamage * 3
elseif variant == "Rainbow" then
    petDamage = petDef.baseDamage * 5
end
```

This value is stored as `newPet.damage`. Later, `getPetDamage` does:

```lua
local baseDamage = pet.damage or 0  -- already 3× or 5×
...
if pet.variant == "Shiny" then
    baseDamage = baseDamage * 3   -- now 9×
elseif pet.variant == "Rainbow" then
    baseDamage = baseDamage * 5   -- now 25×
end
```

The pre-existing pattern for Golden was to bake the 2× into `pet.damage` at conversion time and *not* apply it again at runtime — the old `getPetDamage` had no golden check. This PR introduces a golden check (`if pet.golden then baseDamage = baseDamage * 2`), breaking that contract and making Golden 4× effective.

The cleanest fix: remove the variant/golden multipliers from `getPetDamage` entirely and keep the baked-at-creation values as canonical. Alternatively, store raw `baseDamage` at hatch/conversion and let `getPetDamage` be the single source of truth for all multipliers — but that requires migrating existing golden pet data.

## LuckyEggs bonus interpretation

The `luckyMultiplier` is derived as:

```lua
local luckyBonus = PetService._upgradeService.getUpgradeBonus(player, "LuckyEggs")
local luckyMultiplier = (luckyBonus > 0) and luckyBonus or 1
```

If `getUpgradeBonus` returns values like 2, 3, 4 (pure multipliers), this is correct. If it returns values like 0.5, 1.0, 1.5 (additive bonus percentages), then a player with LuckyEggs level 1 returning `1.0` would already double their variant chance, and the formula should be `1 + luckyBonus` instead of using `luckyBonus` directly. The existing codebase's `StrongPets` usage in `getPetDamage` (`baseDamage * strongBonus`) suggests the upgrade service returns multipliers, but confirming for LuckyEggs specifically would settle this.
