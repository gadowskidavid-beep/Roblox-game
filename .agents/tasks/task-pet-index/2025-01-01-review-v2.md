# Pet Index collection book with first-discovery gating (v2)

Adds per-player discovery tracking (`discoveredPets` dictionary) and a Pet Index UI showing all pets across Normal, Golden, Shiny, and Rainbow variants. The "NEW PET!" full-screen overlay only fires once per pet; duplicates get a short toast. The v1 review raised four issues — `isNewDiscovery` DataStore leakage, silent duplicate hatches, hardcoded pet list, and misleading Shiny/Rainbow lock state — all addressed in commit `a951143`.

Watch for: The progress counter "X/16 Discovered" includes Shiny and Rainbow variants in the denominator even though they're unobtainable, making 16/16 unreachable (confirmed). Minor: `isNewDiscovery` is still present on the pet table when `PetInventoryUpdated` fires to the client, though it's stripped before save (confirmed, low severity).

**Verdict**: APPROVED

## High-level view

All four v1 issues are resolved: the field is stripped after firing to the client, duplicate hatches show a toast, the pet list derives from `PetData.Pets`, and Shiny/Rainbow slots render as "Coming Soon."

The remaining rough edge is the progress counter: `totalCount = #petIds * #variants` (currently 16) includes 8 Shiny/Rainbow slots that no server code path can mark as discovered. A completionist plateaus at 8/16. Excluding "Coming Soon" variants from the denominator would make the counter a useful completion signal.

## Progress counter counts unobtainable variants

```lua
local totalCount = #petIds * #variants   -- 4 * 4 = 16
```

Eight of those 16 slots correspond to Shiny and Rainbow, for which no server discovery path exists. The grid correctly labels them "Coming Soon", but the counter doesn't differentiate — a player who has every obtainable pet sees "8/16 Discovered", which reads as half-complete rather than fully-complete.

A minimal fix: count only variants that are not "Coming Soon" in the denominator.

```lua
local obtainableVariants = 0
for _, variant in ipairs(variants) do
    if variant ~= "Shiny" and variant ~= "Rainbow" then
        obtainableVariants = obtainableVariants + 1
    end
end
local totalCount = #petIds * obtainableVariants
```

Alternatively, show two numbers: "8/8 Obtainable · 0/8 Coming Soon".

## `isNewDiscovery` in the inventory event

The execution order in EggService is:

```
PetService.hatchEgg → sets isNewDiscovery on newPet, inserts into data.pets, fires PetInventoryUpdated
EggService fires EggHatchResult (client receives pet with isNewDiscovery)
EggService strips newPet.isNewDiscovery = nil
```

Because `PetInventoryUpdated` fires from inside PetService (before control returns to EggService), the client's inventory handler receives `data.pets` with `isNewDiscovery` still present on the latest entry. Moving the strip to PetService — immediately after `table.insert` but before firing `PetInventoryUpdated` — would eliminate the leak entirely.
