# Pet Index (Collection Book) with first-discovery popup gating

Adds a per-player discovery-tracking system (`discoveredPets` dictionary in DataService) and a new client-side Pet Index UI that renders a 4×4 grid of all pets across all variants. PetService stamps discoveries on hatch (Normal) and golden conversion (Golden), and the "NEW PET!" overlay is now suppressed for pets the player has already seen. A new "I" nav button opens the index; opening it fetches the latest discovery map from the server.

Watch for: Shiny and Rainbow variants appear in the grid but have no server-side discovery path — they will remain permanently locked (confirmed). The `isNewDiscovery` field is persisted inside the player's pet inventory array, bloating save data indefinitely (confirmed). Suppressing the popup for duplicates means the player gets zero feedback on a duplicate hatch — no toast, no abbreviated message (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The discovery data model is a flat dictionary keyed by `petId` (Normal) or `"Golden_" .. petId` (Golden). Keys for Shiny and Rainbow follow the same `Variant_PetId` convention on the client, but the server never writes those keys, so half the grid is permanently undiscoverable.

The popup gating achieves the user-requested "only show once per new pet" goal by early-returning from `showEggHatch` when `isNewDiscovery` is false. This eliminates all duplicate-hatch feedback — there is no lighter notification to take its place.

The UI is a self-contained ScreenGui created at init time and populated on demand via a `GetDiscoveredPets` remote. The grid layout, card construction, and progress counter work correctly. The hardcoded pet list in the client (`{"Buddy", "Whiskers", "Blaze", "Inferno"}`) is a maintenance risk if new pets are added to PetData without updating the UI.

## Shiny and Rainbow variant gap

`PetData.Variants` declares four variants and the client iterates all of them to build discovery keys (`"Shiny_Buddy"`, `"Rainbow_Inferno"`, etc.). On the server, `PetService.hatchEgg` only writes keys of the form `petId` (Normal), and `convertToGoldenPet` writes `"Golden_" .. petId`. No code path ever writes a Shiny or Rainbow key. The progress counter will never reach 16/16 for any player regardless of what they do in the game.

```lua
-- Client key construction (UIController:_refreshPetIndex)
if variant == "Normal" then
    discoveryKey = petId
else
    discoveryKey = variant .. "_" .. petId  -- "Shiny_Buddy", "Rainbow_Buddy", etc.
end
```

If Shiny/Rainbow acquisition mechanics haven't been built yet, the variants should be excluded from the index (or shown with a "Coming soon" state rather than a lock that implies obtainability).

## `isNewDiscovery` leaking into persistent data

`PetService.hatchEgg` sets `newPet.isNewDiscovery = true/false` on the pet table *before* it's inserted into `data.pets`. Because `data.pets` is the array that gets serialized to DataStore, this boolean ships to disk on every save for every pet the player owns. Over time this adds meaningless bytes to the save payload. The field's only consumer is the client-side event handler, which reads it once and discards the value.

The fix: after `EggHatchResult:FireClient(player, newPet)` fires, nil out `newPet.isNewDiscovery` so it never reaches the save path. Alternatively, pass the flag as a second argument to `FireClient` instead of embedding it in the pet table.

## Silent duplicate hatches

```lua
function UIController:showEggHatch(petData, isNewDiscovery)
    if not isNewDiscovery then
        return  -- total silence
    end
    ...
end
```

The 3D egg-crack animation still plays (handled by EffectsController), but the UI confirmation with the pet's name, rarity, and stats is entirely skipped. Players who hatch duplicates will see an egg crack and then … nothing. A short toast ("Buddy hatched — already collected!") would close the feedback loop without the full-screen fanfare.

## Hardcoded pet list in the client

```lua
local petIds = {"Buddy", "Whiskers", "Blaze", "Inferno"}
```

This list mirrors `PetData.Pets` today, but `PetData.Pets` is a dictionary with no guaranteed order. If a fifth pet is added, the index silently omits it. Deriving the list from `PetData.Pets` (with an explicit sort for layout order) removes the coupling.
