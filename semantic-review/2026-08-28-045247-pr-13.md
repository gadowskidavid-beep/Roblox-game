# Persistent potion inventory with atomic post-build publication

QOF-13 changes potion purchases from immediate transient activation to server-authoritative acquisition in the persistent V7 inventory, with five canonical products independently capped at 999. An opaque CurrencyService transaction captures the validated profile, keeps debit and rollback silent, and publishes the committed balance only after inventory mutation and authoritative state construction succeed. Strict V2 contracts, per-player serialization, fail-closed rolling compatibility, and dormant consumption keep effects outside the purchase path. The regenerated place contains the current runtime sources byte-for-byte. **Watch for:** **confirmed / low** Roblox replication, DataStore sessions, multiplayer timing, and device UI behavior remain Studio-only release checks.

**Verdict**: APPROVED

## High-level view

CurrencyService owns an opaque begin/commit/rollback lifecycle over the validated profile reference. Rollback restores that captured table without reacquiring player data, and neither begin nor rollback emits `CurrencyUpdated`.

ShopService holds the player lock across validation, silent debit, one-field mutation, and V2 state construction. Commit emits the only currency update after that state exists; `ShopBuffsUpdated` follows only after the transaction succeeds.

The network accepts only the exact four-field potion DTO. Catalog prices, integer quantity, independent caps, malformed state, legacy strings, `ExtraEquipSlot`, and dormant Auto-Hatch are all resolved server-side.

Potion controls remain disabled until the server advertises V2 `inventoryOnly`. Purchase stores a server-confirmed count but does not activate effects, consume inventory, refresh movement, or start a countdown.

All supplied automated evidence is reproducible: 167/167 Pure-Lua tests, 81 compiled Luau files, 50 JSON/3 Python/1 XML parses, clean `git diff --check`, and byte-exact parity for all 66 generated runtime sources. The documented Studio pass remains necessary for engine-only behavior (**confirmed / low**).

## Captured-profile rollback closes the previous atomicity gap

`beginSpendTransaction` validates once, debits silently, and stores the same profile table with amount and currency behind an identity-based handle (`src/ServerScriptService/Services/CurrencyService.lua:179-198`). `rollbackSpendTransaction` restores that table directly, so a later DataService failure cannot strand the debit. The CurrencyService regression removes lookup availability after begin and verifies exact restoration, no event, and single-use rollback (`tests/CurrencyService.spec.lua:117-132`).

ShopService builds authoritative state before commit and rolls back both mutations for after-spend, after-mutation, and state-build failures (`src/ServerScriptService/Services/ShopService.lua:239-282`). Rollback preserves an absent inventory key rather than materializing zero. Tests verify exact balance/key restoration, no client events, and lock release, including failure of the second profile lookup used by state construction (`tests/ShopService.spec.lua:250-280,325-349`).

## Currency and shop publication follow the committed state

`commitSpendTransaction` consumes the handle and makes the composite transaction's sole `fireCurrencyUpdate` call (`src/ServerScriptService/Services/CurrencyService.lua:200-207`). ShopService reaches it only after inventory mutation and `getShopState` complete (`src/ServerScriptService/Services/ShopService.lua:263-274`); failed pre-commit paths emit neither debit nor refund events.

`ShopBuffsUpdated` runs only after the purchase returns success (`src/ServerScriptService/Services/ShopService.lua:430-435`). Its deep-copied payload is independent from the returned DTO and profile, and a protected replication failure does not reverse committed state.

## Exact request, cap, lock, and no-effect boundaries

Main rejects malformed input before consuming cooldown, and ShopService repeats the V2 shape check at its boundary (`src/ServerScriptService/Main.server.lua:62-84,585-596`). The server supplies item identity, price, quantity, and resulting state; unknown or legacy potion strings fail before debit. Coverage includes 998→999, rejection at 999, per-potion isolation, insufficient funds, malformed profile state, dependency errors, and concurrent lock rejection (`tests/ShopService.spec.lua:176-247`).

The lock spans profile lookup through commit and is cleared after protected execution. `ExtraEquipSlot` retains its price, maximum, rollback, and DTO behavior on the same transaction path; Auto-Hatch stays fail-closed. Player removal clears only transient locks and compatibility buffs.

Purchase does not write persisted or transient active buffs, refresh Movement, consume charges, run Auto-Hatch, or invent optimistic counts. Removing the timer heartbeat and countdown presentation keeps gameplay effects behind QOF-14 consumption.

## Rolling V2 state and generated artifact

The state builder returns fresh V2 inventory, cap, permanent-slot, and legacy-buff projections. Client controls remain `SYNCING` until both capability fields match (`src/StarterPlayer/StarterPlayerScripts/UIController.lua:3465-3499`), so old servers cannot interpret new potion buys; new servers reject old potion strings without charging (`UIController.lua:3541-3544,3604-3648`).

`BATTLE_PETS.rbxlx` parses and contains the expected 64 ModuleScripts, one Script, and one LocalScript, with all 66 sources byte-identical to the source tree. The full suite passes 167 tests; 81 Luau files compile; all 50 JSON and 3 Python files parse; and `git diff --check 58e0664` is clean.
