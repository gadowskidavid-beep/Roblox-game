# Central atomic profile and currency transactions

QOF-25 adds one exclusive mutation owner per loaded profile, converts the listed paid composites to silent currency reservations, and gates persistence until commit or exact rollback. `DataService` closes the begin/save race before cloning, while domain-first settlers and strong handles preserve failed work for lifecycle retry. The migrated paths avoid debit/refund replication and make post-commit notifications terminal. Two production paths still miss the roadmap’s uniform transaction boundary.

**Watch for:** **confirmed, blocking** — the live campaign free-hatch path bypasses the new profile owner; **confirmed, blocking** — Enchanting builds its required success DTO only after the currency PONR and can return a paid success with no DTO.

**Verdict**: NEEDS_CHANGES

## High-level view

`ProfileTransactionService` is the common profile-level admission boundary. Currency reservations register it before returning, `DataService` marks a save in progress before checking for an existing owner, and leave/shutdown close admission before repeatedly settling retained profiles independently.

Upgrade Tree, Shop, Potion upgrades, paid/manual Egg hatches, Auto-Hatch access, Machines, and Enchanting reserve without changing the live balance. Their rollback closures restore owned domain state before canceling currency; the central owner and service records preserve failed work for retries.

The owner-backed free hatch exists only behind `EggService.hatchFree`. The actual one-time campaign egg reward still calls legacy `PetService.hatchEgg(..., true)`, so the production free hatch never enters that flow.

Enchanting commits currency before constructing its Contract V1 response. A post-commit DTO failure is intentionally returned as `success == true` with `state == nil`, contrary to QOF-25’s mutation → full DTO → single commit order.

## Central owner closes the save race

```text
composite service
    -> CurrencyService reservation / direct free-hatch owner
        -> ProfileTransactionService owner
            -> DataService save admission and pending-owner check
```

`DataService.savePlayerData` sets `_saving[userId]` before testing `hasPending`; `ProfileTransactionService.begin` rejects both closed admission and an in-progress save. Pending owners are rejected before `DataSchema.cloneForPersistence`, and autosave skips them. Leave retains the exact Player/profile incarnation, while shutdown retries profiles independently against a shared deadline.

Currency reservation leaves the live balance and `CurrencyUpdated` untouched. Commit applies one debit and releases the exact owner; rollback only cancels the reservation, without a credit or client event. Additive rewards can raise the live balance while reserved, and commit subtracts the fixed amount from that current balance.

## Campaign special eggs bypass free-hatch ownership

The added free branch acquires `ProfileTransactionService.begin` before charge or pet mutation, and `EggService.hatchFree` reaches it (`src/ServerScriptService/Services/EggService.lua:585-629, 741-753`). **Confirmed, blocking:** no production caller uses `hatchFree`; the boss reward calls `CampaignService._petService.hatchEgg(player, rewards.SpecialEgg, true)` and marks `campaignBossRewards` afterward (`src/ServerScriptService/Services/CampaignService.lua:528-542`). That legacy path commits the pet under only an inventory lease, with no central owner or strongly retained rollback (`src/ServerScriptService/Services/PetService.lua:606-657`).

The new tests prove only the unused `EggService.hatchFree` entry point. Route campaign special-egg claims through an owner-backed EggService operation and keep pet creation plus the claim marker under the same retryable transaction; calling `hatchFree` and setting the claim after its owner commits would preserve the gap.

## Enchanting commits before its Contract V1 DTO exists

Enchanting installs a domain-first settler and mutates the exact pet, then invokes `commitSpendTransaction` immediately after `beforeCommit` (`src/ServerScriptService/Services/EnchantingService.lua:351-406`). **Confirmed, blocking:** `EnchantingService.roll` builds the response only after that PONR at lines 508-515. If the later profile lookup fails, it returns `true, nil, nil`; `tests/EnchantingService.spec.lua:440-451` codifies this outcome.

The roadmap requires every inventoried composite, including Enchanting, to build the full DTO before its single commit (`QOF-22-31-ROADMAP-README.md:289-299`). Build a projected post-roll state—including next revision and post-debit availability—before commit, retain it on the transaction, and restore any pre-PONR revision write with the pet if projection or commit fails. Return the retained DTO after commit even when inventory replication fails.

## Retry and terminality boundaries

Rollback is domain-first: Upgrade Tree restores its exact purchase table/key, Shop its inventory key, Potion its field/revision, Auto-Hatch its expiry/session projection, Egg its pets then Shiny charges, and Machine/Enchant their pets before currency cancellation. Failed cancellation remains reachable through the central settler; services with inventory leases retain local transaction records as well.

Post-PONR notifications are protected and do not trigger compensation. QOF-26’s Potion/Shiny/AutoDrink lease races, QOF-27’s input-removal-before-RNG ordering, and QOF-28’s Auto-Hatch V2 contract are explicitly deferred and are not findings here.

## Automated evidence misses both blockers

Canonical and reverse Luau runs pass 393/393 tests. `git diff --check`, Python compilation, and generated-place verification pass, with all 79 runtime sources byte-identical. Egg tests call `EggService.hatchFree` directly rather than the campaign route, while Enchanting tests positively expect the nil post-commit DTO.
