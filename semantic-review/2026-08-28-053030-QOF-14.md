# Server-authoritative potion consumption, upgrades, and hatch buffs

QOF-14 turns the QOF-13 potion inventory into an authoritative consumption runtime with independent timed sources, persistent upgrades, Auto-Drink, and charge-backed Shiny hatch rolls. The final Auto-Drink fix constructs the owned-state offer as an explicit nullable value, and the regression suite asserts that ownership removes it. Persistence compatibility, timed caps, revisions, and paid-manual hatch transactions remain intact. **Watch for: confirmed — live Roblox Studio UI, multiplayer scheduling, and rolling DataStore deployment validation remain operational release checks outside the automated environment.**

**Verdict**: APPROVED

## High-level view

V8 stores canonical timed sources under their buff type and dual-writes a private `potionBuffSources` compatibility mirror. QOF-13 preserves that unknown root field, allowing V8 to recover source identity after an older rolling server drops structured `activeBuffs`; independently validated copies merge by later expiry and persistence snapshots rebuild the mirror from canonical state.

Manual consumption and Auto-Drink share the authoritative preflight and mutation lock. Exact-cap timed sources are rejected before mutation, near-cap sources intentionally consume one potion for the remaining headroom, distinct buff types consume slots, and Auto-Drink acts only online on explicitly selected sources.

Per-session revisions prevent stale client snapshots from replacing newer state. Paid manual hatches reserve Shiny charges for the first N rolls and commit them only with a successful pet transaction; rollback restores charges, pets, and currency, while bypass and free hatches do not consume charges.

Auto-Drink ownership now has a consistent server/UI contract. The server omits the purchase offer once owned, so the client no longer enables an `OWNED` control that can only be rejected.

## Explicit nullable Auto-Drink offer

`upgradeOffers` initializes `autoDrinkOffer` to nil and populates it only while `upgrades.autoDrink ~= true`. This avoids Lua's truthy/fallback expression pitfall and aligns the offer-driven UI enablement with ownership state. `PotionService.spec.lua` purchases Auto-Drink and immediately asserts `getState(player).upgradeOffers.AutoDrink` is nil, closing the exact regression from the previous pass.

## QOF-13 rolling persistence and source caps

Canonical state keeps Luck and Mega Luck as independent source timers inside one `luck` buff type. The V8 normalizer validates canonical and mirrored sources independently, drops malformed, expired, unknown, and non-timed entries, clamps valid expiries to the 30-day horizon, chooses the later valid expiry, and rebuilds `potionBuffSources` from the merged canonical result.

The regression suite simulates QOF-13 removing structured timed `activeBuffs`, downgrading the schema version, and preserving the unknown mirror. A subsequent V8 migration restores Luck, Mega Luck, Speed, and Coin sources with their identities intact; persistence cloning resynchronizes a changed canonical expiry without exposing the mirror in client data.

## Consumption cap, revision, and Auto-Drink boundaries

The same availability check feeds the DTO and locked consume path. A source exactly at `now + MaxTimedBuffSeconds` is rejected without inventory, revision, or event mutation; a source one second below the cap consumes one potion and clamps to the cap. Multiple sources of the same type share one slot, Duration applies only at timed consumption, Shiny charges cap at 30, and expiry cleanup advances revisions and refreshes movement when speed changes.

Auto-Drink persists only catalog-whitelisted selections and runs only for online players. It processes selected potions in catalog order, drinks a timed potion only when that source is absent or expired, and drinks Shiny only when no charges remain. Manual and automatic consumption share the lock and rollback boundary.

## Paid-manual Shiny transaction boundary

Only validated paid manual intent enables Shiny charge consumption. The service reserves at most the batch count, boosts exactly the first reserved rolls, and commits charges only after pet inventory succeeds. Any preparation, spend, or inventory failure restores the prior charge state together with pet inventory and currency; station-bypass and free hatches remain excluded.

Tests cover successful partial reservation, exact rollback after an injected post-inventory failure, and bypass/free exclusions alongside the existing atomic batch assertions.

## Verification and live-runtime boundary

The pure-Lua suite passes 192 tests with zero failures. All changed Luau production sources compile, generated-place verification confirms byte-exact parity across 65 ModuleScripts, one server Script, and one LocalScript, and `git diff --check` is clean.
