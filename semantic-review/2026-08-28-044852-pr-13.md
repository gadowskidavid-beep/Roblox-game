# Persistent potion purchases without consumption

QOF-13 replaces immediate potion activation with server-authoritative purchases into the existing V7 `potionInventory`, capped independently at 999 per canonical potion. The approach uses an exact V2 request, per-player serialization, catalog-owned prices, a capability-gated inventory UI, and retained ExtraEquipSlot/Auto-Hatch compatibility while consumption stays dormant. The transaction does not yet meet its documented rollback and event-boundary guarantees: refund is best-effort through the same profile lookup that can fail during state construction, and the debit is replicated before commit. **Watch for:** **confirmed / high** loss of Diamonds when rollback credit cannot reacquire the profile; **confirmed / medium** pre-commit `CurrencyUpdated` events despite the stated no-event-before-commit boundary.

**Verdict**: NEEDS_CHANGES

## High-level view

Potion requests cross the trust boundary as an exact four-field V2 DTO; the server rejects client price/effect data, unknown and legacy potion strings, and quantities other than one. A per-player lock encloses validation, debit, one-count mutation, state construction, and rollback, while V7 normalization and persistence already whitelist canonical IDs and cap each count at 999.

The rollback path restores the inventory key first and then calls `CurrencyService.creditRaw`. That refund performs a fresh profile lookup, so it cannot guarantee the advertised all-or-nothing result when profile access is the state-build failure or is otherwise unavailable (**confirmed / high**).

`CurrencyService.spend` emits `CurrencyUpdated` immediately after debit, before inventory mutation and authoritative state construction. Failed transactions can therefore expose a temporary debit followed by a refund event, contradicting the documented commit/event boundary even though `ShopBuffsUpdated` itself remains post-commit and protected (**confirmed / medium**).

The client enables potion purchases only after receiving `contractVersion = 2` with `purchaseMode = "inventoryOnly"`; old servers leave potion controls fail-closed, while new servers reject old potion strings without debit. Purchase state shows stored counts rather than active timers, and the server purchase path does not write buff state, refresh Movement, consume charges, or run Auto-Hatch.

The supplied automated evidence is reproducible: 164/164 Pure-Lua tests pass, 81 tracked Luau files compile, 50 JSON files, 3 Python files, and the XML place parse, `git diff --check` is clean, and the place verifier confirms all 66 runtime sources byte-for-byte. Roblox replication, DataStore sessions, UI input/layout, and multiplayer timing remain explicitly pending Studio checks (**confirmed / low**).

## Rollback can preserve the inventory but lose the debit

`executePurchase` debits through `CurrencyService.spend`, mutates the captured profile, and builds state through `ShopService.getShopState` before marking the context committed (`src/ServerScriptService/Services/ShopService.lua:247-266`). On failure, `rollbackChargedPurchase` restores the mutation but refunds through `creditRaw(player, ...)`, which resolves the profile again (`ShopService.lua:239-243`; `CurrencyService.lua:188-201`). If profile access fails during state construction and remains unavailable for refund, the inventory key is restored but the Diamonds remain deducted; the caller only receives `Purchase rollback failed` (**confirmed / high**).

The state-construction regression test does not exercise this production dependency chain. It makes `dataService.getPlayerData` fail after the first call, but its local `currencyService.creditRaw` mock writes directly to the captured `profile` and never asks DataService for that profile (`tests/ShopService.spec.lua:88-93,302-322`). The test therefore proves the rollback callback, not the real refund behavior under the injected fault.

Make debit/refund one transaction over the already validated profile: a CurrencyService transaction primitive can capture the profile, apply a silent debit, expose an exact rollback against that same table, and publish currency only after commit. At minimum, add a bonus-free raw profile refund API and an integration test using the real CurrencyService where a persistent state-build/profile lookup fault occurs after debit; assert exact balance restoration, exact key restoration, lock release, and no client events.

## Currency replication crosses the declared commit boundary

`CurrencyService.spend` mutates the balance and calls `fireCurrencyUpdate` immediately (`src/ServerScriptService/Services/CurrencyService.lua:172-183`). Only afterward does ShopService mutate inventory and construct the V2 state (`src/ServerScriptService/Services/ShopService.lua:247-266`). A rollback calls `creditRaw`, which sends a second balance event, so clients can observe an uncommitted debit and then its compensation (**confirmed / medium**).

The ShopService tests replace CurrencyService with a mock that records balance changes but emits no `CurrencyUpdated`; their “no event” assertions count only `ShopBuffsUpdated`. This misses the observable event ordering while the QOF-13 document says the service “only then replicates” and claims “No event before commit” (`docs/QOF-13-persistent-potion-inventory.md:34,70-71`).

Defer currency publication until the inventory mutation and DTO build have committed, and emit one final currency update on success. Rollback before commit should restore both profile fields silently. Add an event-order test with the real CurrencyService/remote mocks that verifies no currency or shop event on every rollback stage and verifies a consistent committed currency/shop-state publication order.
